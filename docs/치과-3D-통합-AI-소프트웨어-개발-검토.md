# 구강스캔·사진·X-ray 통합 3D + AI 소프트웨어 개발 검토

작성일: 2026-11-24 · 참고 자료: [치열 3D 개략 모형](https://najari.github.io/teeth/) (저장소 `najari/teeth`)

"제 계산", "제 추정", "제 제안"이라고 적은 것은 출처가 있는 수치가 아니라 이 문서에서 직접 판단한 것입니다.

---

## 1. 결론

1. **필요한 기술 요소는 대부분 이미 연구나 제품으로 존재합니다.** 3D 치아 분할, X-ray 판독 AI, 구강스캔-CBCT 자동 정합, AI 크라운 설계는 모두 상용 단계입니다. 새로 발명할 것은 적고, 일의 중심은 통합입니다.
2. **현재 가지고 있는 치열 3D 개략 모형이 이 소프트웨어의 뼈대로 쓸 만합니다.** 치아 번호(FDI) 기준 데이터, 치료 단계 전환, 계획에 따라 형상이 바뀌는 규칙이 이미 들어 있습니다. 표준형 치아를 실측 스캔으로, 눈으로 옮긴 소견을 AI와 측정값으로 바꿔 가면 됩니다.
3. **가장 큰 제약은 세 가지입니다.**
   - 사진과 파노라마 X-ray는 구강스캔과 기하학적으로 정확히 겹쳐지지 않습니다. 정밀하게 합쳐지는 것은 구강스캔과 CBCT뿐입니다.
   - "형태 변화 예측" 가운데 자연 변화(마모, 잇몸 퇴축, 뼈 흡수)는 아직 연구 단계입니다.
   - 치아 상태를 AI가 판독해 설명하는 기능은 의료기기 소프트웨어 규제 대상이 될 수 있습니다.
4. **범용 LLM에게 영상을 직접 판독시키면 안 됩니다.** 판독은 전용 모델이 하고, LLM은 그 결과를 문장으로 옮기는 역할만 맡겨야 합니다(5.3절).

## 2. 출발점: 현재 치열 3D 개략 모형

### 2.1 지금 들어 있는 것

| 항목 | 내용 |
|---|---|
| 구조 | `index.html` 파일 하나. three.js r128과 OrbitControls를 CDN에서 불러옴 |
| 형상 | 치아 종류별 표준 치수(mm)와 치열궁 곡선 수식으로 만든 절차적 형상. 스캔 데이터 없음 |
| 데이터 | FDI 번호를 키로 하는 표: 치아별 상태(없음, 뿌리만 남음, 밑동만 남음), 침착물, 잇몸 퇴축 표시값, 치아 위치 미세 조정 |
| 치료 계획 | 치아별 발치, 임플란트(식립 여부 포함), 골이식 종류, 크라운, 폰틱, 브리지 |
| 뼈 | 6개 구역별 뼈 높이 단계값과 설명 문구. 실측 mm가 아닌 표시용 값 |
| 단계 | 치료 전, 발치, 수술 후, 보철 후 |
| 화면 | 방향 5가지, 위턱·아래턱·잇몸·뼈·빈 자리 표시 전환, 벌림, 치아나 뼈를 누르면 설명 표시 |
| 근거 | 사진, X-ray, 견적서를 눈으로 보고 옮김. "진단 자료가 아님"을 명시 |

참고로 README의 단계 이름(현재, 발치 예정, 치료 후)은 페이지의 4단계와 맞지 않아 갱신이 필요합니다.

### 2.2 이미 맞게 잡힌 설계

- **FDI 번호가 모든 데이터의 키입니다.** 3장에서 보듯 사진과 X-ray는 치아 번호 단위로 연결하는 것이 현실적이므로, 이 구조는 그대로 확장할 수 있습니다.
- **단계(stage)가 일급 개념입니다.** 계획 표에서 단계별 형상을 규칙으로 만들어 냅니다. "치료 과정에 따른 보철물 변화"의 절반은 이 방식으로 해결됩니다(6.1절).
- **근거와 한계를 화면에 적어 둡니다.** AI 소견이 들어오면 이 부분이 출처·확신도 표시로 발전합니다.

### 2.3 목표와의 차이

| 영역 | 현재 | 목표 |
|---|---|---|
| 치아 형상 | 표준형 | 구강스캔에서 잘라 낸 개별 치아 메시 |
| 뿌리와 뼈 | 표준 길이, 구역별 단계값 | CBCT가 있으면 실측, 없으면 "추정"으로 표시 |
| 소견 | 사람이 눈으로 옮김 | 전용 AI 모델 결과 + 출처 + 확신도 + 사람 확인 여부 |
| 사진·X-ray | 모형에 반영만 됨 | 치아를 누르면 해당 사진과 X-ray 영역이 함께 표시 |
| 데이터 위치 | 코드 안에 직접 기입 | 별도 JSON(또는 DB)으로 분리 |
| 보철물 형상 | 표준형 | AI 설계 결과 또는 기공소 설계 파일 |
| 변화 | 계획에 따른 단계 전환 | 계획 시뮬레이션 + 시점 간 실측 비교 + 예측 |

## 3. 데이터 통합: 무엇이 실제로 "3D로 합쳐지는가"

| 조합 | 통합 방식 | 성숙도 | 근거 |
|---|---|---|---|
| 구강스캔 + CBCT | 기하학적 정합. 치관은 스캔에서, 뿌리와 뼈는 CBCT에서 가져와 하나의 모델로 융합 | 상용 | AI 정합 도구 검증에서 전악 평균 부호 편차 4μm, RMSD 114μm, 하우스도르프 거리 940μm ([출처](https://pubmed.ncbi.nlm.nih.gov/39743133/)). Relu의 자동 정합은 31쌍으로 검증([출처](https://creator.relu.eu)). 융합 모델 연구 DDMA([출처](https://pmc.ncbi.nlm.nih.gov/articles/PMC10499902/), [출처](https://arxiv.org/abs/2203.05784)) |
| 구강스캔 + 구내 사진 | 사진의 카메라 자세를 추정해 스캔에 겹침. 스캔에 색을 입히거나 사진 위에 분할 결과를 투영 | 연구 | PMTSeg(CVPR 2026), AI4TRT(IJCAI 2025). 병원 스캔과 스마트폰 사진 사이의 정밀한 강체 정합은 어렵다는 보고도 있음([출처](https://arxiv.org/abs/2310.11106)) |
| 구강스캔 + 파노라마 | 기하학적 정합 불가(파노라마는 휘어진 단층 투영). 치아 번호 단위로 연결 | 연결은 쉬움, 3D 복원은 연구 | 파노라마에서 3D 치아를 생성하는 PX2Tooth는 IoU 0.793 수준 |
| 구강스캔 + 치근단·바이트윙 | 치아 번호 단위로 연결 | 연결은 쉬움 | 2D-3D 정합은 연구 단계 |
| 사진만으로 3D | 생성 모델이나 가우시안 스플래팅으로 복원 | 연구 | TeethDreamer는 사진 5장으로 챔퍼 거리 0.167mm, 하우스도르프 거리 2.11mm. 스플래팅 기반 치아 메시는 구강스캐너보다 부정확하다는 2025년 보고 |

정리하면 다음과 같습니다.

- **기하학적 통합**은 구강스캔 + CBCT에서만 믿을 만합니다. 뿌리와 뼈까지 실측으로 넣으려면 CBCT가 필요합니다.
- **사진과 일반 X-ray는 의미적 통합**, 즉 "이 치아 번호에 해당하는 사진 영역과 X-ray 영역"을 연결하는 방식이 현실적입니다. 현재 모형이 FDI 기준이므로 이 방식과 잘 맞습니다.
- 파노라마에서 뿌리 모양을 생성해 3D에 넣을 수는 있지만, 그것은 측정이 아니라 추정입니다. 화면에서 실측과 구분해 표시해야 합니다.

## 4. 목표 구조

```
입력            구강스캔(STL/PLY/OBJ) · 구내 사진 · 파노라마/치근단/바이트윙 · (CBCT) · 치료 계획
                     │
전처리          치아 분할과 FDI 번호 부여(스캔, X-ray, 사진 각각)
                     │
통합            스캔+CBCT 기하 정합 │ 사진·X-ray는 FDI 단위 연결(+ 카메라 자세 추정)
                     │
소견 추출       X-ray 판독 모델 · 스캔 기반 소견(마모, 퇴축, 우식 의심) · 사진 기반 소견
                     │
환자 모델       치아별 기록: 형상, 소견[출처, 확신도, 확인 여부], 단계별 계획
                     │
설명·시뮬레이션   소견을 문장으로 변환(LLM) · 단계별 형상 생성(규칙 + AI 설계)
                     │
출력            웹 3D 뷰어(three.js): 단계 전환, 치아 선택 시 설명과 원본 영상 표시
```

환자 모델의 치아 한 개 기록은 예를 들어 다음과 같은 모양이 됩니다(제 제안, 값은 예시).

```json
{
  "fdi": 16,
  "geometry": { "crown": "scan", "root": "standard", "mesh": "meshes/16.ply" },
  "findings": [
    { "type": "wear", "source": "ios-model", "confidence": 0.82, "reviewed": false },
    { "type": "periapical-lesion", "source": "pano-model", "confidence": 0.64, "reviewed": true,
      "evidence": { "image": "pano_2026-11.png", "bbox": [812, 340, 60, 58] } }
  ],
  "plan": [
    { "stage": "prosthesis", "action": "crown", "material": "zirconia", "mesh": "design/16_crown.stl" }
  ]
}
```

`geometry.root`가 `standard`인지 `cbct`인지 `generated`인지, `findings`의 출처가 사람인지 어느 모델인지를 기록해 두면 화면에서 실측과 추정을 구분해 보여 줄 수 있습니다.

| 설명 문장 생성 | MMOral, OPGAgent, PanDent | Diagnocat 리포트 | 5.3절 참조 |

### 5.2 직접 만들 것과 가져다 쓸 것 (제 제안)

- **가져다 쓰기**: X-ray 판독, 크라운 설계. 인허가 제품이 있고 학습 데이터 확보가 어렵습니다. 연구·시제품 단계에서는 공개 모델로 대체하고, 제품화 때 제휴나 API 연동을 검토합니다.
- **공개 모델로 직접 구성**: 3D 치아 분할(Teeth3DS+로 학습된 공개 모델), 스캔 간 중첩과 편차 계산.
- **직접 개발**: 환자 모델(데이터 구조), 통합 뷰어, 단계 시뮬레이션, 설명 생성 파이프라인. 이 부분이 차별점입니다.

### 5.3 설명 생성에서 LLM의 역할

범용 시각-언어 모델은 치과 영상 판독에서 아직 믿을 수준이 아닙니다.

- 파노라마 20,563장으로 만든 MMOral 벤치마크에서 가장 성적이 좋은 GPT-4o도 정답률이 43.31%였습니다.
- OPGAgent 연구는 시각-언어 모델이 작업별 전용 모델보다 성능이 낮다고 보고하고, 전용 모델을 도구로 호출하는 에이전트 구조를 제안했습니다.
- PanDent 연구는 멀티모달 LLM이 유창하지만 임상적으로 일관되지 않은 보고서를 만든다고 지적했습니다.

따라서 구조는 "전용 모델이 구조화된 소견(JSON)을 만들고, LLM은 그 JSON만 보고 문장을 쓴다"로 잡아야 합니다. LLM이 쓴 문장마다 근거 소견을 연결해 두면 사람이 검증할 수 있습니다.

## 6. "치료 과정에 따른 보철물과 형태 변화 예측" 나누어 보기

같은 "예측"이라는 말 안에 성격이 다른 세 가지가 섞여 있습니다.

### 6.1 계획에 따른 변화: 예측이 아니라 시뮬레이션

발치하면 치아가 사라지고, 임플란트를 심으면 픽스처가 생기고, 보철을 올리면 크라운이 생깁니다. 이것은 계획이 정하는 것이므로 규칙으로 만들면 됩니다. 현재 모형이 이미 이 방식입니다.

확장할 것: 표준형 임플란트를 제조사 라이브러리 형상으로, 표준형 크라운을 AI 설계 결과나 기공소 설계 파일로 교체.

난이도: 낮음.

### 6.2 보철물 형상 생성

"이 자리에 어떤 모양의 크라운이 들어가는가"는 AI 크라운 설계가 답합니다(5.1절). 인접치와 대합치 스캔이 있으면 수십 초 안에 생성되는 수준입니다.

난이도: 가져다 쓰면 낮음, 직접 학습하면 높음.

### 6.3 자연 변화 예측

마모, 잇몸 퇴축, 뼈 흡수, 치아 이동처럼 시간이 지나며 생기는 변화입니다.

- **측정**은 가능합니다. 시점이 다른 구강스캔 두 개를 겹쳐 편차를 재는 방식으로, 마모 모니터링 연구가 이를 보여 줍니다.
- **예측**은 연구 단계입니다. 교정 치아 이동 예측에서 4,218건으로 평균 오차 0.24mm, 1.87°를 보고한 논문이 있으나 학술지 수준이 낮고, 종설도 이 분야를 초기 단계로 평가합니다([출처](https://pmc.ncbi.nlm.nih.gov/articles/PMC12354369/)).
- 발치 뒤 뼈 흡수량이나 임플란트 주위 뼈 변화의 개인별 예측 모델은 이번 조사에서 확인하지 못했습니다.

난이도: 높음. 먼저 "시점 간 변화 측정"을 만들어 데이터를 쌓고, 예측은 그 다음에 검토하는 순서가 맞습니다.

## 7. 이미 있는 제품과의 관계

통합 플랫폼은 이미 대형 업체의 주 전장입니다. 다만 이 제품들은 자사 장비와 클라우드에 묶여 있고 진료실 워크플로 중심입니다. 비어 있는 자리는 다음과 같습니다(제 판단).

- 장비에 묶이지 않고 개방형 파일(STL/PLY/OBJ, DICOM, 사진)만으로 동작하는 도구
- 구강스캔이나 CBCT가 없는 환자도 표준형 모형 + 사진 + 파노라마로 시작해, 자료가 생기는 대로 실측으로 바꿔 가는 점진적 모델(현재 개략 모형이 정확히 이 출발점)
- 치료 단계별 변화를 환자가 이해하기 쉽게 보여 주는 설명 도구

## 8. 개발 단계 (기간은 제 추정)

| 단계 | 내용 | 산출물 | 기간(1인 기준) |
|---|---|---|---|
| 0 | 현재 개략 모형 | 표준형 치아, 계획 기반 단계 전환 | 완료 |
| 1 | 데이터를 코드에서 JSON으로 분리. STL/PLY 불러오기. 공개 분할 모델로 치아별 메시와 FDI 번호 생성. 표준형과 실측을 치아 단위로 섞어 표시 | 실측 치관이 들어간 3D 차트 | 1~2개월 |
| 2 | 사진과 X-ray를 FDI 단위로 연결. 소견 주석 계층(출처, 확신도, 확인 여부). 공개 X-ray 모델로 소견 초안 생성 | 치아를 누르면 소견과 원본 영상이 함께 보이는 뷰어 | 2~3개월 |
| 3 | 단계 시뮬레이션 고도화(임플란트 라이브러리, AI 크라운 연동). CBCT가 있으면 뿌리와 뼈 융합. LLM 설명 생성 | 단계별 보철물 형상과 설명 문장 | 3~6개월 |
| 4 | 시점이 다른 스캔 중첩과 변화 측정. 데이터가 쌓이면 예측 검토 | 변화 지도, 추적 리포트 | 이후 |

1단계에는 실제 구강스캔 파일이 필요합니다. 공개 데이터(Teeth3DS+)로 개발을 시작할 수 있고, 본인 데이터는 중고 구강스캐너나 치과에서 받은 스캔 파일로 확보할 수 있습니다.

## 10. 확인하지 못했거나 주의할 점

- 개략 모형은 저장소의 `index.html`과 README를 읽고 정리했습니다. 3D 화면을 직접 띄워 보지는 못했습니다.
- PMTSeg, AI4TRT, PX2Tooth, TeethDreamer, MMOral, OPGAgent, PanDent, Teeth3DS+의 수치는 조사 중 확인한 값이며 일부는 원문 링크를 이 문서에 남기지 못했습니다.
- 교정 이동 예측 수치(0.24mm, 1.87°)는 검증 수준이 낮은 학술지의 보고입니다.
- 발치 후 뼈 흡수, 임플란트 주위 뼈 변화의 개인별 예측 모델은 조사하지 못했습니다.
- 국내 디지털의료제품법상 이 소프트웨어의 해당 여부와 등급은 확인하지 못했습니다.
- 8장의 기간은 규모감을 잡기 위한 제 추정입니다.
